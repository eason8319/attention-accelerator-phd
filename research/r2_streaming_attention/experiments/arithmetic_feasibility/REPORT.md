# 资源与最小算术可行性实验

实验日期：2026-09-14；整理日期：2026-09-14。完成范围：本地/单卡资源探测、固定 Llama 的原生 FP16 小规模运行、完整语料计数、整数乘加 RTL/综合网表对拍及单元级时序分析。证据来源为本目录 `results/` 的实际机器记录，统一登记于 [experiment.json](experiment.json)。执行审核状态只见[里程碑](../../../../docs/progress/milestones.md#r2-review)。

PPL 前向次数与 GPU 天按当时全程逐 token 前缀（后登记为 `r2-evaluation-v1`）。现行质量门为 [`r2-evaluation-v2`](../configs/evaluation_protocol.json)，不按 v2 重算下列数字。§3.1 的 Qwen 缺失仅指本次检查的缓存；本机后续写入的开发权重见里程碑，不回溯为本实验已加载。

## 1. 实验目的

回答当时资源、工具链与最小算术能否支撑 R2 开发与正式评测排期，以及完整评测是否存在必须预先处理的成本或依赖障碍。本实验不验证低比特缓存、Attention 功能、任务质量或候选创新，也不按后来的 `r2-evaluation-v2` 质量门重估成本。

## 2. 方法与设置

- **资源与模型**：本地 Windows/WSL 只做资源和工具验证；服务器调度器分配 node8 的单张 RTX 6000 Ada，先运行 64×64 FP16 矩阵乘法，再加载协议固定 revision 的 Llama-3.1-8B-Instruct。模型权重、激活、缓存为 FP16，使用 PyTorch SDPA，batch=1；4K/8K/16K/32K 各一次合成输入 prefill，随后预热 2 步、测量 32 步解码。各步骤同步 GPU 后计时，记录有限值、输入哈希和显存峰值。这里的短测不采用正式公开内核基准的 20 次预热、100 次测量、5 轮统计口径。
- **软件**：服务器 Python 3.11.15、PyTorch 2.5.1+cu121、Transformers 5.14.1、tokenizers 0.22.2；分词计数使用 PyArrow 25.0.0。本地 Verilator 5.020、Yosys 0.33；OpenROAD `2.0-17598-ga008522d8` 在固定 Ubuntu 22.04 容器中执行。安装包、容器 ID、库和上游来源见 [依赖声明](runtime/dependencies.json)与[实际工具记录](results/tool_environment/inventory.json)。本地原生 OpenROAD 可执行文件的依赖不齐，经过验证的入口是容器。
- **算术**：一个同步复位、有 valid/保持行为的 `int16×int16+int32` 单周期寄存乘加，结果按模 2³² 截断。175 组极值组合、2,000 组固定种子随机/复位/空拍向量和初始复位，共 2,176 组。Python 整数运算提供期望值，RTL 与映射后的标准单元网表分别执行 Verilator 对拍；不同证据角色的输出独立保留。
- **综合与时序**：使用固定 ORFS 提交中的 Nangate45 typical 库、1.1 V、25°C，Yosys 映射后由 OpenROAD 分析。时钟 1 ns，数据输入/输出外部延迟各 0.1 ns，输入转换时间 0.05 ns，输出负载 5 fF。没有布局布线或导线寄生参数；面积仅为映射单元面积。采用手工最小流程，未验证当前完整版 ORFS 的构建兼容性。
- **成本计数**：读取协议固定版本的 WikiText test，4,358 行以双换行连接，不自动加特殊 token，前置一个 Llama BOS；只分词，不将完整超长文本送入模型。每个窗口重置缓存，首窗最多覆盖 W 个 token，之后每次前进 512，末窗覆盖至语料结尾；每窗需 `窗口长度−1` 次单 token 前向。这是当时质量门的全程逐 token 前缀，不是 v2 的每窗 prefill 压缩 KV。另核对原版 LongBench 压缩包的完整哈希和四个任务成员，统计全体样本及唯一 ID。[预算计算](results/evaluation_budget/budget.json)只输出组合算量和情景估算。

可复现入口：在本实验目录运行 `bash runtime/run_local.sh --output results/<未使用用途>`；资源、模型、分词和预算分别由 `run_resource_probe.py`、`run_model_runtime.py`、`run_token_count.py`、`run_budget_analysis.py` 执行。模型/分词入口显式接收本机模型路径，依赖固定 revision，不依赖服务器绝对路径；每批输出拒绝覆盖非空目录。源码完整不代表已下载模型或具备 GPU。

## 3. 实验结果

### 3.1 资源及原生模型

本地是 i7-13700、24 逻辑线程、约 32 GB 物理内存，仅检测到 Intel UHD 770；WSL 可见内存约 15.5 GiB，适合功能开发与本次小规模综合。服务器实际分配的 RTX 6000 Ada 可见显存为 51,002,867,712 B，计算能力 8.9。64×64 FP16 运算输出有限，相对 FP32 的 L2 误差为 0.000204821。来源：[Windows](results/windows_environment/inventory.json)、[WSL](results/local_environment/inventory.json)、[GPU](results/gpu_environment/inventory.json)。

Llama 所有探测长度的 logits 均有限；原始时序与每步数据见 [summary.json](results/llama_native_fp16_runtime/summary.json)。

| 输入长度 | 一次 prefill / s | 32 步解码中位数 / ms | 分配显存峰值 / GiB |
|---|---:|---:|---:|
| 4,096 | 1.240 | 21.89 | 15.92 |
| 8,192 | 1.025 | 23.47 | 16.88 |
| 16,384 | 2.365 | 26.66 | 18.79 |
| 32,768 | 5.780 | 35.38 | 22.61 |

这些是原生完整 FP16 缓存的资源探测值。首个 prefill 含首次执行开销，不能用 4K/8K 的单次倒序推断长度趋势；32K 的分配器保留显存峰值为 24.29 GiB。协议中的 Qwen2.5-7B-Instruct 与 Qwen2.5-0.5B base 在本次检查的缓存中缺失，未加载；已有 0.5B Instruct 不能替代 base。未证明其他未检查位置也不存在这些模型。

### 3.3 完整评测成本

当前固定分词得到 Llama 共 **289,077 token**，每次完整 PPL 计分 **289,076 token**，详见[原始计数](results/llama_wikitext_tokens/token_count.json)。这是本轮协议计数，不沿用 R1 的历史 token 数。

| 窗口 W | 重置窗口数 | 每格式×布局的串行前向次数 | 按对应长度原生时延估算 / GPU 天 |
|---|---:|---:|---:|
| 4,096 | 558 | 2,285,010 | 0.579 |
| 8,192 | 550 | 4,505,050 | 1.224 |
| 16,384 | 534 | 8,748,522 | 2.700 |
| 32,768 | 502 | 16,449,034 | 6.735 |

四个窗口、四格式、双布局合计，仅 Llama PPL 就有 **255,900,928 次串行前向**。把本次对应长度的 C0 时延套入全部前缀及格式，得到 **89.90 GPU 天**的规划参照；它既不是上下界，也不是 R2 压缩路径的实测时间。若实际每步恒为 5/20/50/100 ms，分别为 14.81/59.24/148.09/296.18 GPU 天。Qwen 的分词和时延尚未测得，不能直接把这些数乘二当作双模型排期。

原版 LongBench 的 qasper/gov_report/hotpotqa/lcc 分别为 200/200/200/500 条，逐任务唯一 ID 检查通过。按双模型、四窗口、四格式、双布局共 **70,400 次样本运行**，生成上限 **10,649,600 token**。RULER 协议组合为 **19,200 次样本运行**、最多 **1,612,800 生成 token**；连续生成另有 **32 次运行、32,768 步**。这些生成上限不包含 prefill 成本，RULER 生成器与任务适配尚未运行，不是实际完成量。来源：[预算及成员哈希](results/evaluation_budget/budget.json)。

## 4. 分析与讨论

现有单卡资源已支持固定 Llama 的原生 32K FP16 小规模探测；KV 几何本身在 32K 时为 Llama 4 GiB、Qwen 1.75 GiB，但该推算不含权重、激活、临时张量、分配器和元数据。不能据此推断后续所有压缩实现、paged 路径或 batch=4 均能装入显存。本地资源可承担物理格式和小 RTL 的功能开发。

主要排期风险来自 PPL 口径。完整语料本身约 29 万 token，窗口每前进 512 都重新逐 token 计算前缀，使其扩展为约 2.56 亿次前向。即使优化后的每步只需 5 ms，单模型仍约 14.8 GPU 天。这个问题应在正式评测前明确预算和口径，不能等到运行中才截断语料或偷偷替换缓存路径。

综合结果验证了工具链和有限向量集内的算术一致性，同时给出有效的负时序结果。当前单周期结构的组合路径过长；后续 RTL 必须根据真实运算、流水级和供给约束重新综合。此整数单元不代表 FP16 乘法、FP32 累加、指数/倒数或 online softmax，不能将其面积乘 1,024 当作 R2 阵列面积。

公开内核目前是“版本及缺口已核对”，并非“可直接运行”。SAW 的后端和 BF16 示例与本项目设备/FP16 协议间存在待验证适配；BitDecoding 的依赖也应与当前 R1 环境隔离。改变后端、精度或量化定义需要如实标记，不能保留官方名称却隐藏实现差异。

## 5. 局限与有效性

- 模型仅为单卡、batch=1、合成输入、每长度 32 个测量步骤；没有正式质量指标、重复轮次置信区间或公开内核吞吐结论，也没有 Qwen、物理低比特或分页路径实测。
- 89.90 GPU 天是 v1 全程前缀口径下、采用当时原生长上下文时延的情景外推；短前缀可能更快，压缩实现和 CPU 调度可能更慢，队列等待、故障重跑、评分/I/O 及其他套件均未计入。GPU 天是累计计算量，不承诺可获得的并行设备或日历完成时间。
- 算术仅做确定性向量对拍，未做全状态形式等价；未布线、没有导线 RC、时钟树、PVT 扫描、SRAM 宏或功耗分析。1 ns 未通过的结果保持原样，理论 1 GHz 不等于综合频率。
- 公共数据的哈希和样本数已核对；RULER 样例生成、LongBench 模板/评分适配与模型停止条件仍属于后续实现。源码及依赖声明本地保全不等于全部模型和上游内核均已安装。
- 服务器仅增量回收本实验已完成的 JSON 与执行源码核验，未覆盖本地已有文件；来源/哈希在项目 `.server-sync/r2-resource-recovery/` 登记。源码、原始结果和依赖在本地，GitHub 默认只接收正式报告与约定配置，不能把报告内本地链接说成云端可直接获取。

## 6. 结论与后续工作

本次资源审计和最小算术实验已完成所声明范围：GPU 可执行原生 FP16 Llama，RTL 与映射网表通过对拍，OpenROAD 能出具实际时序结果。**1 ns 时序未通过，公开内核尚未就绪。** 89.90 GPU 天只约束 v1 全程前缀口径，不是现行质量门的执行预算。这不构成 R2 功能或质量验收。

按 v1 口径，单模型完整 PPL 仍需把数十至数百 GPU 天当作规划参照，不能用这次原生短测直接预约完整双模型任务。现行 [`r2-evaluation-v2`](../configs/evaluation_protocol.json) 已撤回该前缀作为 5%/3% 质量门；v2 成本须等压缩路径短测后再冻结排期，不以本表重算。

同时，正式 GPU 对照前须补齐 Qwen2.5-7B-Instruct、集群侧开发用 0.5B base，以及隔离环境中的公开内核依赖，并决定 SAW 的适用硬件或明确适配范围。本机 `HF_HOME` 是否已有 0.5B base 见里程碑，不计入本实验当时加载结果。后续算术综合需围绕真正的浮点/近似算术和流水化结构开展。是否进入下一执行步骤由用户逐步审核决定，本实验不提前执行物理打包或后续研究步骤。
