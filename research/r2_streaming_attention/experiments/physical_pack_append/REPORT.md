# 物理打包与连续追加实验

实验日期：2026-09-15；整理日期：2026-09-15。完成范围：连续布局的 INT4/KIVI 物理打包与追加、编码一致性、缓存底层存储、输入缓冲复用和分侧对齐预算。证据来源为本目录 [`results/pack_storage_verified/`](results/pack_storage_verified/summary.json)，登记于 [experiment.json](experiment.json)。执行审核状态只见[里程碑](../../../../docs/progress/milestones.md#r2-review)。

本实验不实现分页、KIVI `residual_length=128` 刷窗、流式 Attention 或任务质量，也不出具物理 HBM 事务或能耗结论。

## 1. 实验目的

回答 R1 留下的表示缺口：名义 INT4/KIVI 字节能否变成真实可寻址的 packed 缓冲，以及 decode 式逐 token 追加会不会改写已提交片段或重算统计量。具体要检查：

1. 物理 pack/unpack 是否逐元素恢复 R1 的量化网格，而不是另做一套量化。
2. packed 载荷字节是否等于 R1 的名义 `bytes_payload`，并相对 R1 的 int8/uint8 暂存给出实际缩小。
3. 协议边界长度、页长切开与 C5 未满 32 的 Key 开口组下，追加后的解码是否与同切块的 R1 参考一致；开口组是否独立持有紧凑存储，调用方复用输入是否影响缓存。
4. K/V 各自的整段载荷和元数据按 32 B 对齐时，布局预算与对齐浪费是否可独立核算。

## 2. 方法与设置

- **布局**：冻结 [`pack_layout.json`](../configs/pack_layout.json)（`r2-pack-layout-v1`）。C2/C3 为对称 INT4、`[-7,7]`、低半字节存偶数下标、4-bit 补码；C5 为无符号 4-bit；scale/min 为独立 FP16 密数组，与 group 计数对齐。DMA 对齐只作用于 K/V 两侧的整段 payload、scale、offset 缓冲，量子 32 B，不是已校准的 HBM 突发宽度，也不对每个 group 记录单独垫齐。
- **追加语义**：已提交片段只保留 packed 字节与 FP16 元数据。激活在入口处转为 FP16，与协议 `activation_dtype` 一致。C5 Key 满 32 token 后调用 R1 `encode_kivi_key` 再打包，开口组独立复制剩余 FP16 token，不借用输入或已提交前缀的底层存储；最多保留 31 token，**不是**残差窗 128。调用方可以在追加返回后复用输入。C5 Value 按 token 立即编码。`load` 仅供对拍。
- **存储口径**：`tensor_storage_bytes` 实测缓存载荷、scale/min 和开口组持有的底层存储，按存储身份去重，不只计算视图元素数。`*_allocated`、`allocated_total` 则为 K/V 各自整段缓冲按 32 B 取整的布局预算，不表示 PyTorch 实际分配或 HBM 事务。当前追加片段保存在张量列表中，连续布局表示逻辑序列连续，不等同于已经分配一个连续 DMA 大缓冲。
- **对照**：同一切块上调用未修改的 R1 `kv_codecs`。协议登记的三份语义源码哈希与当前文件一致。C3 逐 token 旋转后 INT4 可能与整段一次 encode 差一档，这是 R1 分页布局中已记录的性质；本实验把参考切成与 cache 相同的追加块，拼接网格后再做一次 decode，以判断打包层有没有改网格。
- **负载**：合成高斯与末维前两通道 $\times 20$ 的 outlier；种子 0/1。几何为协议 Llama KV（8 头、128 维）、Qwen KV（4 头、128 维），另加 $H{=}1,D{=}32$ 的对齐浪费探针，不冒充第三模型。长度取协议 `boundary_lengths` 中的正值。追加方式为整段、逐 token、以及按页长 16 切开。C1 与 C4 只作字节对齐 / 2-bit 原语边界。
- **存储专项**：24 格 C5 所有权检查覆盖长度 17/32/33/257、三种追加切块、连续及带步长的非连续输入；每次追加后立即改写输入，再继续追加并与保留的 R1 参考核对。40 格分侧检查覆盖 C0/C2/C3/C5、长度 0/1/17/32/33 及整段/逐 token 写入。检查器独立遍历六类真实缓冲，不复用实现中的对齐助手。
- **环境**：WSL2 CPU，`r1-kv-baseline` 的 Python 3.11.15、PyTorch 2.13.0+cpu、NumPy 2.4.6、SciPy 1.17.1，PyTorch CPU 线程数为 1。不使用 GPU、模型权重，不向该环境安装 CUDA 扩展。版本见 [run_config.json](results/pack_storage_verified/run_config.json)。

可复现入口（工作目录：`research/r2_streaming_attention/experiments/physical_pack_append`）：

```bash
conda activate r1-kv-baseline
python run_pack_consistency.py --output results/pack_storage_recheck --threads 1
```

输出目录须为空。源码完整不代表已具备 GPU 或后续步骤的分页实现。

| 对象 | 格子数 | 通过 |
|---|---:|---:|
| C0 | 469 | 469 |
| C1（边界） | 1 | 1 |
| C2 | 469 | 469 |
| C3 | 469 | 469 |
| C4 2-bit 原语 | 1 | 1 |
| C5 | 469 | 469 |
| 空缓存 T=0 | 含于上表 | 载荷、缓存底层存储与布局预算均为 0 |

C3 在 `head_dim=128` 与 `32` 上各只有一个旋转矩阵哈希，分别为 `09717404…c84dbf` 与 `977ebcad…56a187`。R1 三份语义源码与 [`evaluation_protocol.json`](../configs/evaluation_protocol.json) 登记哈希一致。

已提交 packed 前缀在继续追加后逐字节不变。C2/C3/C5 的整数网格经 pack/unpack 与 R1 payload 逐元素相同。

### 3.2 实际存储相对名义字节

下表为 Llama KV 几何、$T{=}257$、整段写入、高斯、种子 0 的 K+V 合计，单位字节。INT4 物理载荷等于 R1 名义 0.5 B/元素，并相对 R1 的 int8 暂存缩小一半。C0 无额外打包。

| 格式 | packed 载荷 | R1 名义载荷 | R1 内存网格 | scale | 实测缓存张量存储 |
|---|---:|---:|---:|---:|---:|
| C0 | 1,052,672 | 1,052,672 | 1,052,672 | 0 | 1,052,672 |
| C2 | 263,168 | 263,168 | 526,336 | 32,896 | 296,064 |
| C3 | 263,168 | 263,168 | 526,336 | 32,896 | 296,064 |

$T{=}257$、$H{=}8$、$D{=}128$ 时，INT4 名义载荷为 $2\cdot 257\cdot 8\cdot 128\cdot 1/2=263168$，与 packed 一致。C1 在 $T{=}32$ 上 packed = 名义 = 内存 = 65,536。C4 原语（32 token、4 头、128 维的 Key）packed = 名义 = 4,096，R1 uint8 暂存为 16,384。

C5 开口组与满组（同一几何、整段、高斯、种子 0）：

| $T$ | packed 载荷 | scale | min | Key 开口 token | 开口组底层存储 | 实测缓存张量存储 |
|---:|---:|---:|---:|---:|---:|---:|
| 17 | 8,704 | 1,088 | 1,088 | 17 | 34,816 | 45,696 |
| 32 | 32,768 | 4,096 | 4,096 | 0 | 0 | 40,960 |
| 33 | 33,280 | 4,160 | 4,160 | 1 | 2,048 | 43,648 |
| 257 | 262,656 | 32,832 | 32,832 | 1 | 2,048 | 330,368 |

$T{=}17$ 时 Key 尚未满组，载荷只有立即量化的 Value；$T{=}32$ 时 K/V 均已打包，开口组为空。开口组字节单独记账，不计入低比特名义载荷。

$T{=}257$ 的三种追加模式均只持有 1-token 开口组的 2,048 B。完整主网格中开口组底层大小均等于逻辑元素字节，最大为 Llama 几何的 31-token、63,488 B；缓存张量实际存储也均等于载荷、元数据与开口组逻辑字节之和。

### 3.3 对齐浪费与边界

主几何下各侧 payload/scale/min 缓冲已是 32 B 的倍数，对齐浪费为 0。合成探针 $H{=}1,D{=}32$、$T{=}1$ 的 C2，各侧载荷为 16 B、scale 为 2 B，四个独立缓冲分别向上取整到 32 B：

| 项目 | 缓存张量实际字节 | 分侧布局所需字节 | 对齐浪费 |
|---|---:|---:|---:|
| K+V payload | 32 | 64 | 32 |
| K+V scale | 4 | 64 | 60 |
| 合计 | 36 | 128 | 92 |

完整网格中 324 个格子对齐浪费为正，最大 **92 B**，均来自该小几何的载荷或元数据取整。40 格专项逐侧检查与完整网格的独立计数均通过。页长 15/16/17 与 group 31/32/33 只作为 token 数边界通过切块追加检查，没有分配页表或 DMA 页事务。

24 格 C5 所有权检查在每次追加后清零已输入的 Key、改写 Value，再继续跨组追加。连续和非连续输入均不与开口组共享底层存储，最终 K/V 相对保留输入的 R1 参考最大绝对误差均为 **0**。逐次追加的开口 token、逻辑/底层字节及输入独立性保存在[存储专项](results/pack_storage_verified/storage_contract.json)。

## 4. 分析与讨论

R1 用 int8/uint8 暂存低比特网格、按名义比特记账。本实验把该网格变成 C 序 nibble/bit 装填后，解码仍回到同一套 scale/min。因此“名义 INT4 字节”在连续布局上已经是可核验的物理表示，而不只是报表口径。追加时只编码新切块，历史 packed 前缀不变，满足“物理 pack 只改表示、不重算已提交统计量”。

C5 的 32-token Key 组是打包对齐约束：未满组不能生成 per-channel min/max。把它留在 FP16 开口组并单独计量，避免把未编码 Key 算进 INT4 载荷，也不把最多 31 token 的开口组说成 KIVI 残差窗。Value 沿 channel 分组，单个 token 即可编码，故追加后立即打包。

开口组独立持有剩余 token，使缓存内容不依赖调用方继续保留原输入，也限定了残留 FP16 占用。17 token 的 Key 尚未提交，32 token 时整组转为低比特，因此总存储可以随 token 增加而下降。实际底层存储和输入复用必须分别检查，数值对拍不能替代存储所有权证据。

C3 必须把“encode 切块”和“decode 拼接”分开看。逐 token 旋转后的 INT4 网格可以与整段一次 encode 不同，这来自分块矩阵乘的浮点差越过 round 边界，R1 分页布局已见类似 1 档差异。打包层的有效性只能相对于**同切块 encode、再拼接后一次 decode** 来判断；在该口径下 C3 与 C2 一样通过。不能把逐 token 与整段 encode 的差算成 pack 误差。

32 B 整段对齐在 Llama/Qwen KV 主几何上不增加预算字节，浪费出现在小几何探针上。两侧短载荷相加后恰好为 32 B，并不表示每侧均已对齐；预算必须保持 K/V 侧别。当前规则为先密排各侧载荷和元数据，再对各侧整段缓冲取整。group 记录共址能否减少实际传输，仍属后续布局实验。

`load` 会为对拍物化 float32。存储状态本身是 packed 载荷加 FP16 元数据（及 C5 开口组），还没有流式反量化直接驱动 MAC 的证据。

## 5. 局限与有效性

- 范围为连续布局的物理表示与追加；没有页表、尾页池、四池残差、刷窗轨迹或访存事件计数。
- C5 未实现 `residual_length=128` 的 K/V 不对称刷窗；近期 Value 不会长期留在 FP16。
- 未接入 Attention、模型权重或质量门；合成张量不能代替 WikiText / 任务评测。
- 缓存张量实测不包含 Python 对象、分配器保留内存、C3 固定旋转矩阵，以及 encode、拼接和 `load` 临时工作区；不作为进程峰值内存。
- DMA 32 B 是布局参数；`allocated_total` 是所需容量预算。当前片段张量未实现整段 DMA 缓冲的真实容量分配或地址对齐，不将预算字节称为实测物理事务。
- 对拍在 WSL CPU、torch 2.13.0+cpu 上完成。打包是整数位操作，不依赖 GPU，也不证明集群 GPU 路径已就绪。
- C1/C4 只覆盖原语或单格，不是主线缓存。
- 实验入口与结果在本地保存；GitHub 发布范围遵循根规则，未入库数据不视为可从 GitHub 直接获取。

## 6. 结论与后续工作

在声明的连续缓存范围内，物理打包、追加数值一致性、输入所有权、开口组底层存储与分侧对齐预算均已有通过的机器证据。C0/C2/C3/C5 保持同切块 R1 编码，低比特载荷达到名义字节；C5 开口组占用有界且不受调用方复用输入影响。当前证据支持第三步在本报告范围内提交审核。

下一步为分页、残差窗与读写/刷窗/元数据事件计量，须经用户审核后开展。该步骤还需落实页与缓冲分配及真实访存事件，不能用本报告的布局预算替代物理流量证据。
